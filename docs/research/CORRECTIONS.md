### 1. CLAIM: slotIndex is zero-based: the first slot of an epoch has slotIndex = 0, provable from Solana SDK's EpochSchedule::get_epoch_and_slot_index (solana-labs/solana, sdk/program/src/epoch_schedule.rs), since prose RPC docs don't state it explicitly.
**CORRECTION:** The zero-based-slotIndex conclusion is correct and verified, but the source citation needs updating: use anza-xyz/agave (not the archived solana-labs/solana) and sdk/epoch-schedule/src/lib.rs / crate `solana-epoch-schedule` (not sdk/program/src/epoch_schedule.rs, which is only the historical path in older solana-program releases). For a Garmin Connect IQ watch face reading mainnet-beta getEpochInfo, this is moot in practice: warmup is disabled on mainnet (first_normal_slot=0), so slotIndex simply equals absoluteSlot % slotsInEpoch — zero-based — and secondsToNextEpoch can be computed directly as (slotsInEpoch - slotIndex) * avg_slot_time without needing to reason about the warmup-epoch branch at all.

### 2. CLAIM: On fenix 6 (a MIP/"always-active" display), onUpdate() is called at the top of every minute while in low-power mode, and once per second for ~10 seconds after a wake gesture (high-power mode). Separately, in always-active low-power mode, onPartialUpdate() (if implemented) is called once per second, subject to the device power budget.
**CORRECTION:** The claim is mostly right but imprecise/partially wrong on two counts, so "refuted" (not "confirmed") is the correct call given the exact wording:

1. onUpdate() in high-power mode: CONFIRMED as stated. Primary doc (Toybox.WatchUi.WatchFace, developer.garmin.com) says after a wake gesture the watch face gets "full screen updates every second via calls to onUpdate()" and this high-power state lasts "typically about ten seconds." The forum announcement thread corroborates: "typically 10 seconds, the watch face can enable timers and play animations." Both are qualified as "typically," not guaranteed-exact, so treat "~10 seconds" as approximate, which the claim already does.

2. onUpdate() in low-power mode: CONFIRMED as stated — "the system will call onUpdate() at the top of every minute."

3. onPartialUpdate() "called once per second" — REFUTED as literally stated. The primary doc says onPartialUpdate() is called "for the first 59 seconds of every minute," not all 60 — the one second where onUpdate() fires (the minute boundary) is excluded. The forum thread (forums.garmin.com/developer/connect-iq/f/discussion/7371) confirms the mechanism explicitly: "onPartialUpdate gets called every second (if onUpdate hasn't been called that second)." So "once per second" needs the correction: once per second except the second onUpdate() runs, i.e., up to 59 times/minute, not 60.

4. "subject to the device power budget" — directionally correct but underspecified/inconsistent across sources, which matters for a fenix 6 implementer:
   - The official announcement (forums.garmin.com .../changes-to-watch-face-low--and-high-power-modes) states a hard per-call ceiling: "The update must operate under a 20-millisecond time frame."
   - A separate forum thread (forums.garmin.com/developer/connect-iq/f/discussion/7371 and the related /7388 "onPartialUpdate - PowerBudgetExceeded" thread) describes a running/average-based budget, not a strict per-call cutoff: a user reports "If you exceed an avg of 30ms per call, onPartialUpdate is no longer called," and the WatchFaceDelegate API doc (Toybox.WatchUi.WatchFaceDelegate) confirms there's an explicit callback, onPowerBudgetExceeded(powerInfo), fired with an executionTimeAverage figure when the budget is exceeded — implying an averaged, device-reported threshold rather than one universal fixed number.
   So the claim's "subject to the device power budget" is true as a general statement, but it elides that (a) there appear to be two distinct constraints reported across sources (a ~20ms hard per-call limit per the official announcement vs. a ~30ms average-based threshold per developer forum reports) and (b) exceeding it doesn't just throttle updates — Connect IQ calls onPowerBudgetExceeded() and can stop invoking onPartialUpdate() altogether for that watch face, which is a materially stronger consequence than the claim implies.

Net: the onUpdate() timing claims for fenix 6 (MIP, always-active) check out against the primary API doc and the Garmin forum announcement. The onPartialUpdate() claim is refuted on the "once per second" wording (it's 59/60 seconds, deliberately skipping the onUpdate second) and is incomplete on "subject to the power budget," which per multiple independent sources involves both a hard per-call time limit (~20ms, official announcement) and an average-based threshold (~30ms, forum reports) whose violation triggers onPowerBudgetExceeded() and can disable further partial updates — not merely a vague constraint.

### 4. CLAIM: monkeyc (and barrelbuild/monkeydo/mdd/era) are pure bash wrapper scripts invoking `java -classpath monkeybrains.jar com.garmin.monkeybrains.Monkeybrains "$@"`, with no native/x86_64-only code anywhere in the Connect IQ compiler/build toolchain — verified by reading SDK 9.2.0's bin/monkeyc and by monkeyc --version succeeding on an aarch64 host.
**CORRECTION:** Partially right, partially wrong — refuted as stated because it overgeneralizes from monkeyc to the whole toolchain including monkeydo.

TRUE (confirmed by direct inspection of the real SDK 9.2.0 zip, downloaded fresh from developer.garmin.com/downloads/connect-iq/sdks/connectiq-sdk-lin-9.2.0-2026-06-09-92a1605b2.zip, SHA matching sdks.json, 213,780,514 bytes):
- bin/monkeyc (200 bytes) IS exactly a 4-line bash script: `java -Xms1g -Dfile.encoding=UTF-8 -Dapple.awt.UIElement=true -classpath "$MB_HOME"/monkeybrains.jar com.garmin.monkeybrains.Monkeybrains "$@"`.
- bin/barrelbuild, bin/mdd, bin/era, bin/monkeydoc are likewise thin bash scripts that only invoke `java -classpath ... <MainClass> "$@"` against monkeybrains.jar or era.jar.
- bin/monkeybrains.jar contains only .class files (Java 8 bytecode, major version 52 — runs fine under OpenJDK 17) — no embedded native libraries, no .so/.dll/.dylib, confirmed via `unzip -l`. So the *compiler itself* is architecture-neutral Java and will genuinely run on aarch64 with any compatible JRE, as the claimant's own `--version` test suggests.

FALSE / the overgeneralization that is refuted:
- bin/monkeydo (2,773 bytes) is a larger bash script that is NOT a pure passthrough — it parses flags itself and then runs `java -classpath monkeybrains.jar com.garmin.monkeybrains.monkeydodeux.MonkeyDoDeux -f "$PRG_PATH" -d $DEVICE_ID -s "$MB_HOME"/shell ...`. Its own embedded usage text states: "Pushes and runs a Connect IQ executable on the Connect IQ simulator. **The simulator must be running for this command to succeed.**" So monkeydo is functionally coupled to bin/simulator.
- bin/simulator, shipped in the exact same SDK 9.2.0 Linux zip, is **not Java and not bash**. `file` reports it as: "ELF 64-bit LSB pie executable, **x86-64**, version 1 (GNU/Linux), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, ... for GNU/Linux 3.2.0, stripped" — a 29,165,936-byte native binary. bin/connectiq (the Linux launcher for the simulator/IDE) is a bash script whose else-branch on non-Darwin systems directly execs `"$MB_HOME"/simulator`.
- There is exactly one `bin/simulator` in the whole archive and zero files matching `aarch64`/`arm64` anywhere in the SDK zip's file listing — Garmin ships no native aarch64 Linux simulator build. On a headless Ubuntu ARM64 box this binary cannot execute natively (it will fail with "cannot execute binary file: Exec format error" per general ELF-architecture-mismatch behavior, corroborated independently by github.com/multiarch/qemu-user-static issue #60 and other ARM/x86 ELF-mismatch reports) and would require x86_64 emulation (e.g. qemu-user/box64) to run at all — for which Garmin provides no support or guarantee, and which independent sources (a April 2026 Linux Connect IQ setup guide at karnwong.me, and Garmin's own forums thread "Linux SDK" at forums.garmin.com/developer/connect-iq/f/discussion/107/linux-sdk/35957) separately confirm has a history of native-library/OS-compatibility breakage on Linux even on the intended x86_64 target, offering an AppImage as the workaround — with no ARM counterpart mentioned anywhere.

Net correction: "monkeyc --version works on aarch64 with no native code" is accurate and reproducible. But the claim's inclusion of monkeydo among "pure bash wrapper scripts" with "no native/x86_64-only code in the compiler path" is false: monkeydo depends at runtime on bin/simulator, a stripped x86_64-only native ELF binary with no aarch64 build anywhere in the SDK 9.2.0 Linux distribution. So on this headless Ubuntu aarch64 box, you can compile (.prg build via monkeyc) but you cannot run/sideload-test via the simulator path (monkeydo/connectiq) without x86_64 emulation — actual on-device sideloading to a real fenix 6 (via USB mass storage / Garmin Express or ADB-style MTP copy of the .prg, bypassing the simulator entirely) remains unaffected by this limitation since it doesn't invoke bin/simulator.

**CORRECTION:** The bare numeric fact is right but the "System 3/4-era, NOT System 5/6/7" characterization is wrong, because API Level and Connect IQ System version are two different axes and Garmin explicitly decouples them for legacy hardware.

1) API level 3.4 — CONFIRMED on the primary source. Fetching https://developer.garmin.com/connect-iq/compatible-devices/ (a JS-rendered Gatsby table; raw HTML has no data, it loads client-side, so I used a rendering fetch) shows every fenix 6-family row with column "API Level" = 3.4:

 - fēnix 6S Pro / 6S Sapphire / 6S Pro Solar / 6S Pro Dual Power → 3.4
 - fēnix 6X Pro / 6X Sapphire / 6X Pro Solar / tactix Delta Sapphire/Solar/Ballistics Ed. / quatix 6X / 6X Solar / 6X Dual Power → 3.4
No fenix 6 variant reaches API 4.x; Garmin developer-forum staff (sabeard) confirmed fenix 6 hardware lacks "graphics pools" needed for CIQ 4.0, so it will never get API 4.x (https://forums.garmin.com/outdoor-recreation/outdoor-recreation/f/fenix-6-series/295304/will-the-fenix6-family-ever-be-updated-to-ciq-api-level-4).

2) "System 3/4-era, NOT System 5/6/7" — REFUTED. Two independent pieces of evidence:
 - the5krunner (https://the5krunner.com/2022/03/31/fenix-6-gets-connect-iq-system-5-latest-ciq-update-now-in-beta/) reports fenix 6 firmware 20.82 (beta, 2022) added "Connect IQ system 5" support across all fenix 6 variants (6, 6S, 6 Pro, 6S Pro, 6X Pro) — i.e. fenix 6 is NOT capped at System 3/4.
 - The Garmin developer forum thread "API, CIQ, SDK, SYSTEM #s" (https://forums.garmin.com/developer/connect-iq/f/discussion/402064/api-ciq-sdk-system-s) gives the explicit mapping Garmin uses: each Connect IQ "System" release ships two parallel API tracks, one for legacy CIQ3-class hardware and one for CIQ4+ hardware — e.g. System 5 = API 3.3 (CIQ3 devices) or API 4.1 (CIQ4+ devices); System 6 = API 3.4 (CIQ3 devices) or API 4.2 (CIQ4+ devices). Under this mapping, a device frozen at API 3.4 is the CIQ3-track device for System 6, not "stuck in System 3/4."

So the correct, precise statement is: every fenix 6 variant is permanently capped at Connect IQ **API level 3.4** (the legacy CIQ3 API track) and will never receive API 4.x/5.x — but the devices themselves have been updated via firmware to participate in newer Connect IQ **System** releases (confirmed through System 5, and per Garmin's own System↔API table, API 3.4 corresponds to System 6's CIQ3 track). "API level" and "System version" are not interchangeable, and the claim's parenthetical equating "API 3.4" with being locked out of "System 5/6/7" is not supported by Garmin's own sources — it is refuted.

Practical implication for the Solana-epoch watch face: target Connect IQ API 3.4 (Monkey C, System 3-class runtime: WatchUi, Background/Bluetooth Low Energy or Web Requests API as available at 3.4, no CIQ4-only APIs like Graphics Pools, Complications framework additions past 3.4, etc.) when building for fenix 6/6 Pro/6S/6S Pro/6X Pro and their solar/sapphire/dual-power/tactix/quatix siblings.

### 8. CLAIM: Data delivered via exit() reaches AppBase.onBackgroundData(data) — called immediately if the foreground app is active, otherwise cached and delivered right after the app's onStart() runs on next launch. AppBase.getBackgroundData() can also pull it and resets to null once consumed.
**CORRECTION:** The onBackgroundData timing description is correct and confirmed at the cited URL: AppBase.onBackgroundData(data as Application.PersistableType) as Void is called immediately if the main app is active, otherwise the payload is cached and delivered right after onStart() completes on next launch. However, getBackgroundData() is NOT a method on Toybox.Application.AppBase — it does not appear anywhere on the cited AppBase.html doc page. It is instead a method of the separate Toybox.Background module (Background.getBackgroundData(), documented at developer.garmin.com/connect-iq/api-docs/Toybox/Background.html). Its real purpose is to be called from inside the background delegate to see what data is currently queued-but-undelivered to the main process (so it can be merged with new results before the next Background.exit()); when called from the main/foreground process it always returns null. The 'resets to null once consumed' detail is real but applies to the queued background-side data, not to something AppBase exposes.

14. Background services are registered via AppBase.getServiceDelegate() as [System.ServiceDelegate]. When triggered, the returned delegate's event method runs, then the process MUST call Background.exit(data) or System.exit(); if it doesn't, the OS force-terminates it after 30 seconds.

17. onEnterSleep() means "the device is entering low power mode" — terminate active timers and prepare for once-per-minute updates. onExitSleep() means "the device is exiting low power mode" — timers/animations may be started here, in preparation for once-per-second updates. Both are API level 1.0.0.
18. Background.exit(backgroundData) accepts String, Number, Float, Boolean, Char, Long, Double, Array, or Dictionary (nested Array/Dictionary allowed, null values allowed). Data size limit is 'approximately 8 KB'; exceeding it throws Background.ExitDataSizeLimitException and the process does NOT exit (must retry exit() with less data). exit() is a no-op if called from the foreground app process.
